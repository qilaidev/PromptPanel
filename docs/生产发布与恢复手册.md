## 已修复：`.app` 根目录未封存内容导致签名无效（2026-07-28）

**背景（必读，不要回退）。** 打包脚本原先在签名与校验**之后**，往 `.app` 根目录补三个指向 `Contents/Resources/*.bundle` 的相对软链接（`GRDB_GRDB.bundle` / `KeyboardShortcuts_KeyboardShortcuts.bundle` / `PromptPanel_PromptPanel.bundle`），因为 SwiftPM 生成的 `Bundle.module` 访问器只在 `Bundle.main.bundleURL/<Package>_<Target>.bundle` 一个路径找资源包，而这个路径对 `.app` 来说就是 bundle 根目录。

代价是签名**真的无效**，不是"仅告警"：`codesign --verify PromptPanel.app` 退出码 1，输出 `unsealed contents present in the bundle root`。后果是用户下载后带 quarantine 首次启动被 Gatekeeper 拦截，Sparkle 也会因为校验不过而拒绝安装更新——也就是说本文档要求的 `spctl --assess` 证据当时根本拿不到。

已实测确认：`.app` 的 `CodeResources` 位于 `Contents/_CodeSignature/`、路径相对 `Contents/`，根目录条目**无法**被封存；在签名**之前**放好软链接同样报同一错误（做过对照实验）。删掉软链接后 `codesign --verify --deep --strict` 立即返回 0。

**修复方式。** 运行期真正依赖 `Bundle.module` 的只有 `KeyboardShortcuts` 的 `Utilities.swift`（`NSLocalizedString(self, bundle: .module, ...)`，仅在 `RecorderCocoa` 判定新快捷键"已被主菜单/系统占用"时触发，触发即 `fatalError` 崩溃）。另外两个是死重量——本仓库源码不引用 `Bundle.module`，GRDB 也不引用（其资源包只有 `PrivacyInfo.xcprivacy`）。

因此：

- 新增 `Sources/PromptPanel/Features/Shared/HotkeyRecorderField.swift`，只用 `KeyboardShortcuts` 的公开非 UI API（`setShortcut` / `getShortcut` / `Shortcut(event:)` / `isEnabled`）自绘快捷键录制控件，替换 `SettingsView` 里的 `KeyboardShortcuts.Recorder`。录制期间会临时置 `KeyboardShortcuts.isEnabled = false`，否则 Carbon 注册的现有热键会先吃掉按键、导致无法重录同一组合。
- `build-app.sh` 不再创建任何根目录软链接。
- `release-readiness.sh` 的签名校验**取消了全部豁免**：只要再出现 `unsealed contents present in the bundle root` 就直接判失败。

**已知取舍。** 失去了库自带的"该快捷键已被 <某菜单项> / 被系统占用"弹窗——这两个判定用的是库的内部 API。macOS 遇到被占用的组合会静默让原持有者优先，用户看到的现象是"按了没反应"，所以设置页 hint 和 FAQ 都提示换一个组合。Esc 取消、Delete 清除的交互保持不变。

## 对外发版硬门禁（必须在打 GitHub Release 之前完成）

`scripts/release-readiness.sh` 默认形态、本机 ad-hoc 验证、CI 跑过的 `macos-release-readiness.yml` 都**不能**替代以下三步。每次对外发版前，必须在一台同时具备 Developer ID Application 证书和 `notarytool` keychain profile 的机器上完整跑一遍，并把输出粘贴到本文档底部"本次发布证据"小节。

```bash
./scripts/release-readiness.sh \
  --public-distribution \
  --sign-identity "Developer ID Application: <Your Name> (<TEAMID>)" \
  --sparkle-public-ed-key "<你的 Base64 公钥>" \
  --output-dir /tmp/promptpanel-release

./scripts/notarize-app.sh \
  --app-path /tmp/promptpanel-release/PromptPanel.app \
  --archive-path /tmp/promptpanel-release/PromptPanel-<short>+<build>-macos.zip \
  --keychain-profile <AC_NOTARY>

spctl --assess --type execute --verbose=4 /tmp/promptpanel-release/PromptPanel.app
codesign -d --entitlements - --xml /tmp/promptpanel-release/PromptPanel.app | grep -c disable-library-validation   # 必须为 0
```

期望证据：
- `release-readiness.sh` 输出 `App binary architectures: x86_64 arm64`——对外包必须是通用二进制，缺任一片直接判失败（README/FAQ 承诺同时支持 Apple Silicon 与 Intel）。
- `release-readiness.sh` 末尾输出 `Public distribution precheck passed`。
- 签名校验**没有任何豁免**：一旦出现 `unsealed contents present in the bundle root` 直接判失败，防止把 Gatekeeper 会拦截、Sparkle 会拒绝安装的包发出去（见上一节）。
- `notarytool submit` 返回 `Accepted`，记录 submission UUID。
- `spctl --assess` 输出必须包含 `source=Notarized Developer ID`，否则未公证。
- `codesign -d --entitlements - --xml` 输出**不得**包含 `com.apple.security.cs.disable-library-validation`（grep -c 为 0）；release-readiness 内部会断言其缺失，若混入会直接 fail。库校验必须保持启用。
- `release-readiness.sh` 输出 `Update channel embedded: SUFeedURL=https://tytsxai.github.io/PromptPanel/appcast.xml`——缺 feed URL 或公钥会直接判失败（见"自动更新通道"一节）。

> **关于 `com.apple.security.cs.disable-library-validation`（已于 2026-07 移除）**
> 该 entitlement 会关闭 hardened runtime 的库校验，允许进程加载任意有效签名（含 ad-hoc、不同 Team ID）的 dylib，扩大代码注入攻击面，因此**不再随分发包携带**。
> 依据：`build-app.sh` 会用与主 app 相同的 `--sign-identity` 重签 `Sparkle.framework` 及其全部嵌入 helper（`Installer.xpc` / `Downloader.xpc` / `Autoupdate` / `Updater.app` / 嵌套 dylib），使全体加载代码共享同一 Team ID，从而在不关闭库校验的前提下通过校验；Sparkle 官方文档亦明确该 entitlement 只在 ad-hoc/开发签名时需要，Developer ID 分发不需要。
> 该结论已在本机用对照实验验证根因（Team ID 不匹配才会触发库校验拒绝加载 Sparkle）。**唯一必须在带 Developer ID 证书的机器上补验的一步**：正式签名 + 公证后启动 app，手动触发一次更新检查（`UpdaterService.checkForUpdates`），确认 Sparkle 的 Installer/Downloader 路径在无该 entitlement 时仍正常工作。若发现回归，可回滚本次改动（entitlements + build-app.sh + release-readiness.sh + 本文档）后重新评估。

未拿到上述四条同时通过的证据前，**不要在 GitHub 上打 tag、不要 publish release、不要把 zip 上传到任何分发位置**。

## 自动更新通道（已定型）

| 项 | 值 |
| --- | --- |
| Feed URL（`SUFeedURL`） | `https://tytsxai.github.io/PromptPanel/appcast.xml` |
| feed 源文件 | `release/appcast.xml`（入库，由 `generate-appcast.sh` 写回） |
| 发布方式 | `.github/workflows/publish-appcast.yml` → GitHub Pages（只部署这一个文件） |
| 安装包托管 | GitHub Releases 资产，`https://github.com/tytsxai/PromptPanel/releases/download/<tag>/<zip>` |

**为什么必须在第一个公开二进制之前定死。** `SUFeedURL` 和 `SUPublicEDKey` 写在已安装 app 自己的 `Info.plist` 里，客户端只会去轮询它自己那份地址。第一个公开包一旦漏配或用了临时地址，所有装到它的用户永远收不到更新，只能手动重新下载——没有任何补救手段。因此 `release-readiness.sh --public-distribution` 现在会：

- 未传 `--sparkle-feed-url` 时自动填入上表的 canonical 值；传了别的值会告警
- 未传 `--sparkle-public-ed-key` 时直接判失败
- 打包后断言 `.app` 的 `Info.plist` 里确实存在 `SUFeedURL` / `SUPublicEDKey`，且 feed URL 与本次请求一致

**一次性准备（只有你能做）：**

1. 生成 EdDSA 签名密钥，私钥进当前用户 Keychain，公钥打印到终端：

   ```bash
   .build/artifacts/sparkle/Sparkle/bin/generate_keys
   ```

   把打印出来的 `SUPublicEDKey`（Base64 公钥）记录到密码管理器。私钥永不入库、永不明文外传；换签名机用 `generate_keys -x` 导出、`-f` 导入。

2. 确认仓库 Settings → Pages 的 Source 是 **GitHub Actions**（本次已通过 API 设为该模式）。

**每次发布：**

```bash
# 1. 签名 + 公证 + 出包（feed URL 自动取 canonical 值）
./scripts/release-readiness.sh --public-distribution \
  --sign-identity "Developer ID Application: <Your Name> (<TEAMID>)" \
  --sparkle-public-ed-key "<你的 Base64 公钥>" \
  --output-dir /tmp/promptpanel-release
./scripts/notarize-app.sh --app-path ... --archive-path ... --keychain-profile <AC_NOTARY>

# 2. 建 GitHub Release 并把公证后的 zip 作为资产上传
gh release create v<version> /tmp/promptpanel-release/PromptPanel-<version>+<build>-macos.zip

# 3. 生成并合并 feed（暂存目录只放这一次的 zip！）
mkdir -p /tmp/promptpanel-appcast
cp /tmp/promptpanel-release/PromptPanel-<version>+<build>-macos.zip /tmp/promptpanel-appcast/
./scripts/generate-appcast.sh --archives-dir /tmp/promptpanel-appcast --tag v<version>

# 4. 推送 feed，工作流自动部署到 Pages
git add release/appcast.xml && git commit -m "release: appcast v<version>" && git push
```

第 3 步的"只放这一次的 zip"不是习惯问题：`generate_appcast` 会用当前前缀重写它找到的每一个包的下载 URL，而我们的包按 tag 分散在不同 Release 下，旧 zip 留在暂存目录就会把已发布条目改写成 404。脚本已加硬守卫，详见 `docs/部署说明.md` 4.5.1。

## 当前发布基线

- **依赖版本已锁定**：`Package.resolved` 现在纳入版本控制（不再被 `.gitignore` 忽略）。`Package.swift` 里 GRDB 是 `7.0.0..<7.9.0` 区间、Sparkle 是 `from: "2.9.1"`（即任意 2.x），没有锁文件时不同机器/不同时间构建出的发布包可能带着不同的依赖版本，而 QA 只验过其中一个。升级依赖时显式跑 `swift package update`，把 `Package.resolved` 的变更单独提交并重跑发布门禁。
- 发布前先在“运行健康”确认：数据库路径正常、最近备份存在、近 7 天执行统计可见。
- 更新通道已定型：feed 为 `https://tytsxai.github.io/PromptPanel/appcast.xml`，由 `release/appcast.xml` 经 GitHub Pages 发布（见上一节）。未注入 `SUFeedURL` / `SUPublicEDKey` 的构建（例如本机 ad-hoc QA 包）更新检查保持禁用。
- `./scripts/build-app.sh` 默认生成 ad-hoc 签名 `.app` 与 zip，便于本机验证；面向外部分发前，仍需补齐正式 Developer ID 签名/公证链路。
- `./scripts/release-readiness.sh` 已提供一键发布就绪检查：会校验脚本语法、`scripts/check-docs.sh`、`swift build` / `swift test`、release 打包、签名校验、隔离数据目录启动冒烟，以及基于启动备份的恢复演练。
- 如果当前机器缺少 `xctest`，只能显式使用 `--allow-build-only-tests` 做降级预检；这不是对外公开分发的最终门禁。
- 发布门禁会按本次 `.app` 的 `CFBundleShortVersionString` / `CFBundleVersion` 定位对应 zip 并校验签名，避免输出目录里残留旧 zip 时误验错包。
- `./scripts/notarize-app.sh` 已提供公证/贴票据脚本；当机器已具备 Developer ID 签名和 `notarytool` keychain profile 后，可直接把已签名产物送审并完成 staple / Gatekeeper 复核。
- 每次启动会自动做一次启动维护：WAL checkpoint、清理 30 天前执行日志、按需生成启动备份、仅保留最近 7 份自动启动备份。
- 手动点击“立即备份”生成的备份不会被自动启动清理策略裁掉，可作为发版前保底备份。
- 如果数据库升级失败，应用现在会保留原始数据库并直接报错退出，不再把迁移错误误判成数据库损坏后自动重建空库。

## 发布产物生成

标准打包命令：

```bash
./scripts/build-app.sh
```

标准发布前自检命令：

```bash
./scripts/release-readiness.sh --output-dir /tmp/promptpanel-ready-check
```

如果当前机器只有 Command Line Tools、缺少 `xctest` runner，只能做本机预检：

```bash
./scripts/release-readiness.sh --allow-build-only-tests --output-dir /tmp/promptpanel-ready-check
```

这不是最终对外发布验收；正式发布前仍应在完整 Xcode 环境跑不带降级参数的检查。

常用参数：

```bash
./scripts/build-app.sh --sign-identity "Developer ID Application: Your Name (TEAMID)"
./scripts/build-app.sh --short-version 1.1.1 --build-version 4
./scripts/build-app.sh --sparkle-feed-url "https://example.com/appcast.xml" --sparkle-public-ed-key "BASE64_EDDSA_PUBLIC_KEY"
./scripts/build-app.sh --debug --no-archive
./scripts/release-readiness.sh --public-distribution --sign-identity "Developer ID Application: Your Name (TEAMID)"
./scripts/notarize-app.sh --app-path dist/PromptPanel.app --archive-path dist/PromptPanel-1.1.1+4-macos.zip --keychain-profile "AC_NOTARY"
```

产物位置：

- `.app`：`dist/PromptPanel.app`
- 压缩包：`dist/PromptPanel-版本号+构建号-macos.zip`

打包脚本当前会：

- release 构建默认产出 `arm64 + x86_64` 通用二进制（本机构建 + 交叉构建另一片 + `lipo -create`）；`--debug` 默认只构建本机架构；可用 `--arch universal|native` 覆盖
- 把 SwiftPM resource bundle 放入 `Contents/Resources`
- 把 `Sparkle.framework` 放入 `Contents/Frameworks`
- 为可执行文件补 `@executable_path/../Frameworks`
- 清理 `.app` 产物内的扩展属性，避免 `Sparkle.framework` 携带 `com.apple.FinderInfo` 等 xattr 导致严格签名校验失败
- 未传正式证书时做 ad-hoc 签名，便于本机 QA
- Sparkle feed URL 和 EdDSA 公钥必须成对注入，只提供其中一个时打包会失败
- 传入正式证书时执行 Developer ID 签名，但公证流程仍需单独跑通

## 标准发布流程

1. 在当前版本主界面点击“立即备份”，确认备份目录下生成新的 `.sqlite` 备份。
2. 先运行 `./scripts/release-readiness.sh`；如果只是本机 QA 且当前机器缺少 `xctest` runner，才允许加 `--allow-build-only-tests`；如果准备对外发包，至少加上 `--public-distribution --sign-identity ...` 做正式签名预检。
3. 生成已签名产物后，运行 `./scripts/notarize-app.sh --app-path ... --archive-path ... --keychain-profile ...`，完成 notarization、staple 和 Gatekeeper 复核。
4. 如需单独生成产物，运行 `./scripts/build-app.sh`，确认 `dist/PromptPanel.app` 和 zip 产物生成成功。
5. 退出应用。
6. 替换新的应用包。
7. 启动新版本。
8. 检查“运行健康”和“最近执行记录”。
9. 至少做一次真实执行，确认自动粘贴或复制兜底都正常。

补充说明：

- `--public-distribution` 当前只做“正式发包前硬门槛预检”，不会代替 Apple notarization / staple；这一步仍需在真实证书和账号环境下单独完成。
- 如果本机缺少 `xctest` runner，脚本会明确提示；只有显式传入 `--allow-build-only-tests` 才会降级为测试包构建校验，这种机器不应作为最终对外发布前的最后验收机。
- 发布冒烟阶段会在隔离目录创建数据库和启动备份，再用该备份恢复到隔离目标目录；这一步失败时，应优先排查备份结构、恢复脚本和 schema 兼容性，不要继续发版。

## 回滚流程

1. 退出应用。
2. 使用 `./scripts/restore-backup.sh /absolute/path/to/backup.sqlite` 恢复指定备份。
3. 重新启动应用并核对数据。

补充说明：

- `restore-backup.sh` 会先验证备份完整性和必要表结构，再把当前 `promptpanel.db` / `-wal` / `-shm` 移到 `Recovery/manual-restore-时间戳/`，最后写入目标备份。
- 恢复写入使用 staging 副本，不直接从原始备份路径覆盖目标库；即使误选了目标库本身或复制过程失败，也不会在搬走旧现场之后才发现恢复源不可用。
- 如果你需要保留多个发版前人工备份，优先使用主界面“立即备份”，不要依赖自动启动备份替代。

## 数据异常恢复

- 如果启动时数据库损坏，应用会把原始文件移动到 `Recovery/recovered-时间戳/` 后自动重建新库。
- 如果启动时提示“数据库升级失败”，说明是迁移/代码问题，不是应用替你恢复成功了；此时应先停发当前版本并保留现场，不要强行重启覆盖。
- 数据库损坏自动恢复后，应优先从最近备份恢复，不要直接覆盖掉 `Recovery/` 中的现场文件。
- `Recovery/` 目录用于排障和人工比对，确认无用后再清理。
