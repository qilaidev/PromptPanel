# PromptPanel 部署说明

更新时间：`2026-06-09`

## 1. 结论先说清楚

PromptPanel 的正式运行态只有一种：

- **本地 macOS 桌面应用**

用户要求里的“本地 / 容器 / 服务器”三种部署方式，需要按真实能力区分，而不是一概写成“支持”。

## 2. 部署方式矩阵

| 方式 | 当前状态 | 适用场景 | 不能做什么 |
| --- | --- | --- | --- |
| 本地 macOS 运行 | 推荐，且是唯一正式运行态 | 开发、日常使用、桌面验收、真实发布包运行 | 无 |
| 本地 macOS 打包/发布 | 推荐 | 构建 `.app`、签名、公证、回归、自测 | 不能替代最终用户安装验证 |
| macOS CI / 自托管 runner | 支持 | `swift build`、`swift test`、打包、签名校验、自动化预检 | 不能替代真实桌面人工兼容性验收 |
| Linux 容器运行产品 | 不支持 | 无 | 无法提供 `AppKit`、`NSPanel`、全局热键、登录启动、GUI 会话 |
| 普通服务器运行产品 | 不支持 | 无 | 不能成为终端用户的实际运行环境 |
| 服务器托管发布产物 | 支持 | 托管 `.zip`、`appcast.xml`、Sparkle 更新文件 | 不能运行 PromptPanel 本体 |

## 3. 为什么容器和服务器不是产品运行态

这是由项目能力边界决定的：

- 面板依赖 `NSPanel`
- 全局快捷键依赖 `KeyboardShortcuts` / macOS 桌面事件
- 自动粘贴依赖辅助功能权限和 GUI Session
- 登录启动依赖 `SMAppService`
- 用户价值来自“当前桌面前台应用上下文中秒开并注入内容”

所以：

- **容器** 最多只能做辅助构建或静态文件托管，不能替代客户端运行
- **服务器** 最多承担发布产物分发、Sparkle appcast 托管或 macOS CI 角色，不能代替用户本地客户端

## 4. 本地部署

### 4.1 环境要求

- macOS `14.0+`
- `zsh`
- Swift `5.10`
- 开发建议安装完整 Xcode
- 仅安装 Command Line Tools 时可以构建，但通常缺少 `xctest`；不能把 build-only 测试当成完整测试执行
- 如果要做对外发布，还需要：
  - Developer ID Application 证书
  - `notarytool` 可用环境
  - Apple notarization keychain profile

### 4.2 仓库结构要点

- 仓库根目录：脚本、CI、PRD、版本化 `docs/`
- SwiftPM 包根目录：仓库根目录

因此构建命令不要写错位置：

```bash
swift build
swift test
```

### 4.3 本地开发 / 构建

最基础构建：

```bash
swift build
```

测试：

```bash
swift test
```

如果本机缺少 `xctest`，只能做测试包构建校验：

```bash
swift build --build-tests
```

生成本地可打开的 `.app`：

```bash
./scripts/build-app.sh --debug --no-archive
open dist/PromptPanel.app
```

说明：

- `build-app.sh` 会把 SwiftPM 二进制和资源组装成真正的 `.app`
- 这是桌面验收时应优先使用的形态
- **架构**：release 构建默认产出 `arm64 + x86_64` 通用二进制（先本机构建，再交叉构建另一片，最后 `lipo -create` 合并）；`--debug` 默认只构建本机架构，避免本地开发循环翻倍。可用 `--arch universal` / `--arch native` 显式指定。
- 交叉构建的部署目标取自 `Info.plist` 的 `LSMinimumSystemVersion`，`check-docs.sh` 已保证它与 `Package.swift` 的 `.macOS(...)` 一致。
- `Sparkle.framework` 本身已是通用二进制，资源 bundle 与架构无关，因此只需要合并 app 自身的可执行文件。
- 只想快速验证时可加 `--arch native` 跳过交叉构建：

```bash
./scripts/build-app.sh --arch native --no-archive
```

### 4.4 本地发布前检查

标准入口：

```bash
./scripts/release-readiness.sh --output-dir /tmp/promptpanel-ready-check
```

它会统一执行：

1. shell 脚本语法检查
2. `scripts/check-docs.sh` 文档同步门禁
3. `swift build`
4. `swift test`
5. release `.app` + zip 打包
6. 签名校验
7. 隔离数据目录下的启动冒烟
8. 基于启动备份做隔离恢复演练

如果当前机器只有 Command Line Tools、缺少 `xctest`，可以显式降级为本机预检：

```bash
./scripts/release-readiness.sh --allow-build-only-tests --output-dir /tmp/promptpanel-ready-check
```

这只证明测试包可构建，不能作为对外发布前最终门禁。

如果只改文档、脚本说明、配置说明或 README，也要单独跑：

```bash
./scripts/check-docs.sh
```

这条门禁会检查必备文档、Markdown 本地链接、陈旧数据库/热键/部署说法、`PROMPTPANEL_*` 环境变量覆盖、顶层维护脚本是否被文档提到，以及 CI 是否包含文档同步检查。

如果准备做对外发包预检：

```bash
./scripts/release-readiness.sh \
  --public-distribution \
  --sign-identity "Developer ID Application: Your Name (TEAMID)"
```

### 4.5 本地正式打包 / 公证

正式打包：

```bash
./scripts/build-app.sh \
  --sign-identity "Developer ID Application: Your Name (TEAMID)"
```

补 Sparkle 更新元数据：

```bash
./scripts/build-app.sh \
  --sign-identity "Developer ID Application: Your Name (TEAMID)" \
  --sparkle-feed-url "https://example.com/appcast.xml" \
  --sparkle-public-ed-key "BASE64_EDDSA_PUBLIC_KEY"
```

公证与贴票据：

```bash
./scripts/notarize-app.sh \
  --app-path dist/PromptPanel.app \
  --archive-path dist/PromptPanel-1.1.2+5-macos.zip \
  --keychain-profile "AC_NOTARY"
```

### 4.5.1 Sparkle 自动更新接入

自动更新是直接下载分发形态下唯一的线上修复通道，因此正式发布必须把它配通，否则用户装到的版本无法被推更新。

**一次性：生成 EdDSA 签名密钥（每台签名机只需一次，私钥存进 Keychain）**

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys
```

命令会把私钥写入当前用户 Keychain，并打印出应放进 `Info.plist` 的 `SUPublicEDKey`（Base64 公钥）。把这个公钥作为 `--sparkle-public-ed-key` 传给 `build-app.sh`。私钥永远不要提交或明文外传。

**托管形态（已定，不要改）**

| 项 | 值 |
| --- | --- |
| Feed URL（`SUFeedURL`） | `https://tytsxai.github.io/PromptPanel/appcast.xml` |
| feed 源文件 | `release/appcast.xml`（入库） |
| 发布方式 | `.github/workflows/publish-appcast.yml` 把该文件部署到 GitHub Pages |
| 安装包托管 | GitHub Releases 资产，URL 形如 `https://github.com/qilaidev/PromptPanel/releases/download/<tag>/<zip>` |

Feed URL 会写进每个已分发二进制的 `Info.plist`，**对已安装客户端不可变更**——换地址等于让老用户永远收不到更新。`release-readiness.sh --public-distribution` 已把它设为默认值并断言构建产物里确实带上了。

安装包放 GitHub Releases 而不是 Pages：Pages 有站点体积上限、也不是二进制分发通道，把每次发布的 zip 提交进仓库还会永久撑大 git 历史。Pages 上只有 `appcast.xml` 一个文件，工作流也只部署这一个文件，不会把文档目录镜像到第二个域名。

**每次发布：生成并签名 appcast.xml**

先完成 `build-app.sh`（注入 feed URL + 公钥）与 `notarize-app.sh`（签名、公证、贴票据、重打 zip），把最终 zip 作为资产上传到对应 tag 的 GitHub Release，再生成 feed：

```bash
mkdir -p /tmp/promptpanel-appcast
cp dist/PromptPanel-<version>+<build>-macos.zip /tmp/promptpanel-appcast/
./scripts/generate-appcast.sh --archives-dir /tmp/promptpanel-appcast --tag v<version>
git add release/appcast.xml && git commit -m "release: appcast v<version>" && git push
```

脚本会从 SPM 产物里定位 Sparkle 的 `generate_appcast`，按 `--tag` 推导下载 URL 前缀，用 Keychain 里的私钥签名，把结果合并回 `release/appcast.xml`；推送后工作流自动部署到 Pages。无法访问 Keychain 的 CI 机器可用 `--ed-key-file` 传入导出的私钥文件（`generate_keys -x`），该文件不得入库。

> **暂存目录必须只放这一次发布的包。** `generate_appcast` 会用当前 `--download-url-prefix` 重写它在暂存目录里找到的**每一个**包的 enclosure URL。我们的包按 tag 分散在不同 Release 下，所以上一版的 zip 只要还留在暂存目录里，它已发布的条目就会被静默改写成新 tag 的 URL（404），那个版本的用户从此更新不了。实测：两个 zip 同时在场时工具报 `updated 1 existing update` 并改写旧 URL；只放新 zip 时报 `updated 0 existing updates`，旧条目原样保留。脚本已对此加了硬守卫，`--allow-multiple-archives` 只在刻意用同一前缀重建整个 feed 时才用。

脚本还会在写回 feed 前做两项断言，工作流在部署前重复同样的检查：

- **存在 `sparkle:edSignature`**：缺私钥时 `generate_appcast` 只告警不报错，而没有签名的 feed 比没有 feed 更糟——客户端配了 `SUPublicEDKey` 会拒绝每一个条目，更新通道看着是活的却永远装不上东西。
- **XML 合法**：Sparkle 解析不了的 feed 会让每次更新检查静默失败，症状是"用户就是收不到更新"，很难往回查。这条已经踩过一次：XML 注释里**不允许出现双连字符**，而 `release/appcast.xml` 的说明注释里写了脚本的 `--` 开头参数，导致整个 feed 无法解析。在这个文件里描述命令行参数时避开裸的双连字符。

**自动检查策略**：`Info.plist` 已默认开启每日自动检查（`SUEnableAutomaticChecks=true`、`SUScheduledCheckInterval=86400`），但保持“提示后再安装”（不静默安装）。若某次发行不想带自动检查，把 `SUEnableAutomaticChecks` 改回 `false` 即可；未配置 feed URL / 公钥的构建里更新能力本就保持禁用。

### 4.6 本机安装验证

如果只是把当前本地版本安装到这台 Mac，推荐路径是：

```bash
./scripts/build-app.sh --output-dir dist/install-local
osascript -e 'quit app "PromptPanel"' || true
rm -rf /Applications/PromptPanel.app
cp -R dist/install-local/PromptPanel.app /Applications/PromptPanel.app
xattr -dr com.apple.quarantine /Applications/PromptPanel.app 2>/dev/null || true
open /Applications/PromptPanel.app
```

安装后要确认实际运行的是 `/Applications/PromptPanel.app`，不要误把 `dist/` 里的开发包当成已安装版本。

## 5. 容器部署

### 5.1 当前结论

- **不支持将 PromptPanel 本体部署到容器里运行**

### 5.2 原因

- Linux 容器没有可用的 AppKit 图形环境
- `NSPanel`、菜单栏、全局快捷键、登录启动都不是容器语义
- 自动粘贴需要用户本机辅助功能权限和图形焦点链路

### 5.3 容器在这个项目里还能干什么

只能做辅助能力，例如：

- 在 macOS 构建完成后，作为静态文件镜像或内部下载页镜像
- 托管 Sparkle 的 `appcast.xml`
- 托管 `.zip` 发布包
- 托管说明页或内部下载页

如果团队一定要写“容器部署方案”，应明确写成：

- **容器用于分发，不用于运行产品**

### 5.4 容器化分发的最低形态

如果团队必须把“容器”纳入交付材料，推荐只写成静态分发容器：

```text
macOS release runner -> signed/notarized PromptPanel.zip + appcast.xml -> static container/image -> users download and run local .app
```

容器镜像里不能放需要用户交互的 PromptPanel 运行进程，也不能把 Accessibility、全局快捷键或目标应用粘贴能力描述为容器能力。

## 6. 服务器部署

### 6.1 当前结论

- **不支持把服务器当 PromptPanel 的运行环境**

### 6.2 可以支持的服务器角色

服务器可以承担下面几类职责：

| 角色 | 是否适合 | 说明 |
| --- | --- | --- |
| 静态文件服务器 | 适合 | 托管 zip、`appcast.xml`、发布说明 |
| macOS CI 机器 | 适合 | 跑构建、测试、打包、公证 |
| 普通 Linux 业务服务器 | 部分适合 | 只能做静态托管或辅助发布，不能运行产品 |
| 远程桌面常驻“替用户运行” | 不适合 | 不符合产品设计，也不稳定 |

### 6.3 推荐的服务器化落地方式

如果需要“服务器参与部署”，推荐这样设计：

```mermaid
flowchart LR
    DEV["开发机 / macOS Runner"] --> BUILD["构建 + 签名 + 公证"]
    BUILD --> ART["静态产物托管: zip + appcast.xml"]
    ART --> CLIENT["用户本地 macOS PromptPanel.app"]
```

这才是和当前架构一致的“服务器参与方式”。

### 6.4 服务器侧发布清单

服务器只接收已经在 macOS 发布机完成验证的产物：

- `PromptPanel.app` 打包生成的 zip
- Sparkle `appcast.xml`（如果当前发行启用 Sparkle）
- release notes / checksums
- 必要时的下载页静态资源

服务器侧不负责：

- 重新签名 `.app`
- 修改 `Info.plist`
- 注入 Sparkle 公钥
- 运行 PromptPanel 进程
- 代替真实 macOS 桌面兼容性验收

## 7. 推荐部署拓扑

### 开发态

- 一台本地 macOS 开发机
- 本地运行 `.app`
- 随代码维护的 `docs/`
- GitHub Actions 做基础回归

### 对外分发态

- 一台 macOS 发布机或 macOS runner
- 一个静态文件托管位置：
  - Nginx
  - S3 + CDN
  - GitHub Releases + 自建 appcast

### 不推荐

- 试图用 Docker 代替客户端运行
- 试图让后端服务器“远程帮用户粘贴”
- 没有完整 Xcode / 证书 / notarization 条件却直接发公网上线包

## 8. 部署时的最低验收标准

无论你采用哪种交付方式，最终都要满足下面几点：

- 打包产物是完整 `.app`，不是裸二进制
- `codesign --verify --deep --strict` 通过
- zip 解压后仍能通过签名校验
- `scripts/check-docs.sh` 通过，文档没有落后于脚本/配置/部署边界
- 应用首次启动能创建数据库和启动备份
- 主界面的“运行健康”可用
- 至少完成一轮真实桌面目标应用兼容性验收

如果这些没过，就不能把“服务器已部署”“容器已准备好”当成交付完成。
